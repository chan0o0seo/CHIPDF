# 원본 분위기에 가까운 한국어 글꼴 선택

이 기능은 에이전트가 원본과 후보 미리보기를 시각 비교하여 선택하는 작업 흐름이다. `font_inventory.py`는 로컬 글꼴의 실제 이름·경로·한글 지원을 검사하며 이미지 유사도 순위나 자동 글꼴 식별 결과를 만들지 않는다.

## 원본 관찰과 후보 수집

새 프로젝트에서는 [web-font-discovery.md](web-font-discovery.md)의 실제 검색·공식 페이지 열람을 후보 선정에 포함한다. 로컬 inventory는 글리프 지원 조사이며 웹 후보 비교를 대신하지 않는다. 폰트 선정 기록을 마지막 포장 단계에서 사후 요약만으로 만들지 말고 후보 비교 시점에 근거를 남긴다.
1. 제목·본문·주석·대사 등 서로 다른 역할의 대표 영역을 원본 PNG/crop으로 확인한다. 명조/고딕/손글씨/붓글씨/장식체, 획 굵기와 대비, 각짐/둥글음, 폭과 밀도, 인쇄물의 분위기를 기록한다. PDF에서 원본 폰트명을 얻을 수 있으면 보조 단서로 사용하되, 부분 내장 이름이나 OCR 추정치만으로 결정하지 않는다.
2. `python <skill-dir>/scripts/font_inventory.py --translations <translations.json> --output <work-dir>/font-inventory.json`으로 설치된 한국어 지원 글꼴을 모은다. 번역 전에는 `--text "한글 제목 본문 가나다 123!?"`로 시작하고 번역 후 실제 문장으로 다시 검사한다. 사용자 제공 글꼴 폴더는 `--font-dir <folder>`를 추가한다. Python 별칭이 실행되지 않으면 workspace dependency 도구가 알려준 실제 Python 실행 파일을 사용한다.
3. `family`, `family_aliases`, `style`, `weight_class`, `width_class`, `panose`와 실제 글꼴 모습을 참고해 역할별 후보 2~3개를 고른다. PANOSE와 숫자 속성은 보조 단서이며 비슷한 분위기를 보장하지 않는다. 후보가 적으면 있는 후보만 비교한다. 사용자 지정 폰트를 우선한다.
4. `covers_requested_text`와 `missing_characters`를 확인한다. 전체 번역에서 기호가 빠지는 후보는 해당 역할에 쓰일 문장만 `--text`로 재검사해 사용 가능 여부를 판단한다. 한글 음절 지원 개수만으로 자모·한자·기호 지원을 가정하지 않는다. 빈 `checked_characters`일 때 `covers_requested_text: true`는 실제 문장 검증 결과가 아니다. `warnings`에 파싱 실패가 있으면 그 파일은 미검증 상태다.

기본 탐색은 시스템 및 사용자 Fonts 폴더의 TTF/OTF/TTC/OTC다. 이외의 위치에 등록된 폰트는 해당 폴더를 `--font-dir`로 지정한다. 수집되지 않은 파일을 지원하지 않는 폰트로 단정하지 않는다. 정적 글꼴과 가변 글꼴, 컬렉션의 각 face는 별도 후보로 기록된다.

## 미리보기 비교와 적용

- 후보 비교에서 폰트를 확정한 뒤 [layout-matching.md](layout-matching.md)에 따라 실제 획 높이와 시각적 중심을 보정한다. 아래의 같은 기준 크기는 초기 폰트 비교용이며 최종 한국어 크기를 원문 숫자에 고정하는 규칙이 아니다. 폰트가 바뀌면 크기와 위치도 다시 검수한다.
- 대표 영역의 동일한 한국어 문장으로 후보별 별도 JSON과 `.twproj`를 만든다. 원본 `source.twproj`에서 각각 적용하여 후보 사이의 이전 변경이 누적되지 않게 한다. 번역·상자·정렬을 동일하게 유지하고 초기 비교에서는 같은 기준 크기와 `--no-fit`을 사용한다. 외형의 차이를 확인한 다음 실제 글자 높이·폭에 맞춰 크기와 줄바꿈을 조정한다.
- `layout.font_family`에는 파일명이 아닌 inventory에서 확인한 family 또는 해당 렌더러가 인식하는 별칭을 사용한다. `--font-file`은 런처에서 엔진으로 전달되는 전역 옵션으로 서브명령 앞에 놓고 필요한 만큼 반복한다. 예: `python <script> --font-file <font.ttf> apply <source.twproj> <translations.json> --output <candidate.twproj> --no-fit`. apply뿐 아니라 preview와 export에도 필요한 글꼴 파일을 전달한다.
- 굵은 face가 별도 패밀리로 제공되면 그 이름을 사용한다. 같은 family의 Regular/Bold를 `font_family`만으로 구별할 수 없는 경우, TTC의 face index나 가변 폰트 축도 JSON에 임의 필드로 추가하지 않는다. 실제 렌더링을 확인하고 지원되지 않는 굵기·축 선택은 ChiPDF 편집기에서 마무리한다.
- 후보별 미리보기와 원본 crop을 실제로 열어 획의 느낌, 굵기, 자폭, 밀도, 가독성을 비교한다. 계열과 분위기를 먼저 맞추고 실제 한글 획·지면 밀도로 최종 결정한다. 일본어와 한국어는 글자 구조가 달라 완전한 외형 일치를 약속하지 않는다. 폰트 파일 로드 성공만으로 선택한 face가 적용됐다고 판단하지 않는다.
- 선택 이유·family·파일 경로·역할·기준 크기·남은 차이를 `<work-dir>/font-selection.json` 또는 서식 메모에 기록한다. 이는 작업 기록이며 translations JSON의 스키마가 아니다. 선택 결과를 역할별 해당 항목의 `layout.font_family`에 반영하고 전체 미리보기 및 최종 PDF를 검수한다. 사용자가 편집 중인 프로젝트에는 적용하지 않는다.

## 로컬 후보가 부족한 경우

웹 검색·비교를 요청받았거나 로컬 후보가 부족하면 [web-font-discovery.md](web-font-discovery.md)를 읽고 공식 샘플 탐색 → 후보 다운로드 → 실제 번역문 비교 → 최종 적용을 수행한다. 이 사용자는 설치 폰트가 적어 웹 후보도 비교하기를 원한다. 프로젝트에 이미 검수한 폰트가 있으면 재사용하고, 새 폰트를 고를 때는 로컬 목록만으로 결론 내리지 않는다. 필요한 무료 폰트는 라이선스를 확인해 작업 폴더에 받고 `--font-dir`로 검사한 뒤 `--font-file`로 로드한다. 사용할 수 있는 후보가 없으면 가장 가까운 사용 가능 후보와 외형 차이를 밝힌다.
